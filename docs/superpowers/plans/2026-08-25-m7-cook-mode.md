# M7 Implementation Plan — Cook Mode + the Closed Loop

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A full-screen, one-step-at-a-time cooking view built for wet hands and a propped-up phone — oversized targets, a wake lock, an ingredient drawer that never loses your place, and concurrent timers — ending in the loop that justifies the whole project: *"Made it?" → rate + note in one gesture.*

**Architecture:** Cook mode is a route (`#/cook/<id>`), not a modal, so it is linkable, back-button-correct, and survives a reload mid-recipe. Step navigation, timer state, and the drawer are pure functions over a small `cookState` object, unit-tested without a DOM. The wake lock and the vibration/audio channels are thin, individually-guarded wrappers — every one of them is unavailable on some real device, and none may throw.

**Tech Stack:** Same as every prior milestone — vanilla ESM, zero build step, `node --test`, zero npm dependencies.

## Global Constraints

- **Touch targets are 56–64px with at least 8px separation.** WCAG's 44×44 is a floor for ordinary UI; wet hands are a motor-impairment analogue and this screen is the one place the plan raises the bar deliberately.
- **Cook-mode text targets 7:1 contrast (AAA), not 4.5:1.** It is read at arm's length, in variable light, with steam on the screen. This constrains which tokens may be used here.
- **Every swipe has a visible tap alternative** (WCAG 2.5.1). Slick fingers make swipe unreliable anyway, so the buttons are the primary control and swipe is the affordance on top.
- **Timer completion fires on three channels — visual, vibration, and sound — never sound alone.** The phone may be silenced, and the cook may be deaf or hard of hearing. Each channel is independently optional and independently guarded.
- **The wake lock must fail silently and never block cooking.** It is unavailable in some browsers, revoked on tab hide, and rejects without a user gesture. A missing wake lock is a dimmed screen, not a broken app.
- **The ingredient drawer must not lose the current step.** Opening it, scrolling it, and closing it returns to the exact same step, with timers still running.
- **Reloading mid-recipe returns to the same step.** Cook state persists to `localStorage` keyed by recipe id. Losing your place because a phone locked and reloaded is the failure that makes people stop using a cooking app.
- **Cook mode never writes on exit.** "Made it?" is an explicit choice. Silently marking a recipe cooked because someone opened cook mode would corrupt the variety data M11 depends on.
- **The closed loop reuses M6's primitives unchanged** — `submitWrite`, the queue, and the `opId` idempotency. M7 adds no new write path.
- **Allergen badges travel into cook mode.** Safety information appears on every surface a recipe name appears; cook mode is not an exception.
- Zero npm dependencies, zero build step, Node >=20 for tests.

### Task 1: Cook state — pure step/timer logic

**Files:** Create `js/ui/cook-state.js`; test `test/cook-state.test.mjs`

**Interfaces:** `initCookState(recipe)`, `nextStep(state)`, `prevStep(state)`, `gotoStep(state, i)`, `saveCookState(recipeId, state)`, `loadCookState(recipeId)`, `clearCookState(recipeId)`.

- [ ] **Step 1: Write the failing tests** — clamps at the first and last step rather than wrapping (wrapping from the last step back to prep is disorienting mid-cook); `gotoStep` rejects out-of-range and non-integer indices; a recipe with zero steps yields a valid state rather than throwing; state round-trips through storage; a corrupt blob yields a fresh state; a stored step index beyond the current recipe's length (the Sheet was edited since) clamps to the last step instead of rendering blank.
- [ ] **Step 2-5: Red, implement, green, commit.**

### Task 2: Timers — concurrent, pure, and persistent

**Files:** Create `js/ui/timers.js`; test `test/timers.test.mjs`

**Interfaces:** `addTimer(timers, {label, seconds, now})`, `removeTimer(timers, id)`, `tickTimers(timers, now)`, `parseDurationsFromStep(text)`.

Timers store an **absolute end timestamp**, never a remaining count. A remaining-seconds counter decremented by an interval drifts, and stops entirely when the tab is backgrounded — which is exactly when a 40-minute bake is running.

- [ ] **Step 1: Write the failing tests** — several timers run at once and are independent; `tickTimers` marks only the elapsed ones as fired; a timer created before a backgrounded gap reports fired on the next tick after resume (prove by advancing `now` past the end, never by real waiting); removing one leaves the others; `parseDurationsFromStep` extracts `40-45 min`, `1 hour`, `90 seconds`, and `1 1/2 hours`, and extracts nothing from a step with no duration; an oven temperature (`400°F`) is never parsed as a duration.
- [ ] **Step 2-5: Red, implement, green, commit.**

### Task 3: Capability wrappers — wake lock, vibration, audio

**Files:** Create `js/ui/device.js`; test `test/device.test.mjs`

**Interfaces:** `requestWakeLock()`, `releaseWakeLock()`, `vibrate(pattern)`, `playAlert()`, `deviceSupport()`.

Every one of these is missing on some real device. Each is individually feature-detected and each swallows its own failure — one unavailable channel must never take down the other two, and none may throw into a click handler.

- [ ] **Step 1: Write the failing tests** with injected fakes — absent `navigator.wakeLock` resolves to null rather than throwing; a rejected request (no user gesture, or a low-battery refusal) resolves to null; absent `navigator.vibrate` is a no-op; `playAlert` with no `AudioContext` is a no-op; `deviceSupport()` reports each channel independently; releasing a lock that was never acquired does not throw.
- [ ] **Step 2-5: Red, implement, green, commit.**

Re-acquire the lock on `visibilitychange` — browsers revoke it whenever the tab hides, so without this the screen starts sleeping again the first time the cook checks a message.

**Files:** Modify `js/views/cook.js`; test `test/cook-view.test.mjs`

- [ ] **Step 1: Write the failing tests** — on the last step, one control offers rating and note together in a single view, not a three-screen wizard; when unpaired (`capabilities.private === false`) the finish screen still appears but offers only "Done", with no rating or note UI and no pairing nag; the note field carries the same autosave draft behaviour M6 established.
- [ ] **Step 2-5: Red, implement, green, commit.**

The whole point of this milestone: rating and note are captured **at the moment the information exists**, in one gesture. If it becomes a separate chore it will never happen, and every variety feature downstream dies with it.

### Task 7: `scripts/export-private.mjs` — the missing backup

Folded in here because it was flagged as a genuine gap at M6 and should not wait.

Every public recipe has a free versioned backup: `data/library.json` is committed on every sync, so git history holds every version. Deliberately excluding private data from that bundle also excluded it from that backup. Accumulated cooking notes are the least replaceable data in the system and currently have **none**.

**Files:** Create `scripts/export-private.mjs`; test `test/export-private.test.mjs`

- [ ] **Step 1: Write the failing tests** — writes both private tabs to the given path; **refuses to write anywhere inside the repository**, with a test asserting a repo-relative path is rejected (an exported notes file committed to a public repo is the exact leak this whole architecture exists to prevent); requires endpoint and token from the environment, never from a file; a fetch failure exits non-zero and writes nothing (same anti-wipe posture as `sync.mjs`).
- [ ] **Step 2-5: Red, implement, green, commit.** Document in `apps-script/README.md`: run it after any meaningful stretch of cooking.
